# V1.6.0 — Mobile layout audit and refactor plan

**Question asked:** why does the theme break when the page switches from desktop
to mobile, and what is the right way to refactor so it doesn't?

**Short answer:** the skin has no concept of a viewport. Three separate
authorities decide "is this mobile", none of them agree with each other, and
none of them agree with the game. The dominant failure is a single line of
reasoning repeated in five places in `UIFoundation.js` — a *static class* test
used to pick the real panel column — which is correct above 1280px and exactly
inverted below it.

Everything in §1–§3 is the mental model. §4 is the audit with evidence. §5 is
the plan.

**Implementation status (2026-09-04):** Steps 1–5 are done. §8 below records
what shipped, what was verified, and what remains.

---

## 1. How the stack actually assembles

### 1.1 Six sheets, one cascade, injected in a fixed order

`content.js:injectPresentationStyles()` injects, in this order:

```
base.css  →  tooltip-engine.css  →  inventory.css  →  skillpanel.css
          →  header.css  →  ui-system.css        (LAST — it wins ties)
```

They are strings compiled into the bundle, injected as `<style data-iw-style=…>`
so the kill switch can remove the complete theme. `StyleInjector.rewriteAssetUrls`
rewrites `url('../assets/…')` to `chrome-extension://…` at injection time, which
is why that exact literal form is mandatory in source.

### 1.2 Three ways a pixel gets its value, in increasing order of authority

1. **Stylesheet rules.** Ordinary cascade. Loses to everything below.
2. **`ui-system.css`'s generic control rule** — `(0,4,1)` + `!important`,
   injected last. Anything on a `<button>` loses to it unless it is in that
   rule's `:not()` chain.
3. **Inline `!important` written by a renderer** — `SkillPanelRenderer.styleButton()`
   and `AtlasService._applySprite()`. No selector can override these.

That ladder is the reason CLAUDE.md tells you to add a hook to the `:not()` chain
rather than escalate specificity. **It also means the skin's responsive CSS can
only reach layer 1.** A `@media (max-width: 600px)` block cannot move a button
that `styleButton()` sized inline — and `styleButton()` has no viewport input at
all. Every geometry it writes (`NAV_BUTTON_W` 26px, the action button 155×44) is
a desktop constant applied at every width.

### 1.3 Art is resolved in two different coordinate systems

- **Atlas sprites** (`AtlasService`, `SkillsArtService`): `background-size` as a
  *percentage pair*, `background-position` as a percentage. Scale-free — these
  survive any viewport. Overriding the size with pixels moves the window onto a
  different region of the sheet.
- **`border-image` sources** (`panel_corners.webp`, `skills_xp_plaque_wide.webp`):
  fixed slice, fixed border-width. `30px 28px` corners paint at 30×28 whatever the
  panel size, by design. The plaque's `--fs-plaque-cap` is derived from its
  *height* (`58 × h / 71`), so a media query that changes `--fs-plaque-h` silently
  re-derives the cap — which is correct, and is why CLAUDE.md warns not to round it.

Per-zone theming layers on top: `HeaderRenderer.applyZoneTheme()` writes
`--iw-zone-atlas` and `--iw-corner-filigree` inline on `<html>` plus a
`data-iw-zone-theme` attribute that nine `:root[data-…]` blocks in `base.css` key
off. **This layer is viewport-independent and is not part of the mobile problem** —
verified below, it works at every width.

### 1.4 The game's DOM: the panel stack exists TWICE

This is the load-bearing fact. IdleWorlds ships the whole panel stack as two
sibling sections (confirmed by this repo's own `claude/probe-panel-order.js`):

```html
<section class="hidden xl:grid …">   <!-- WIDE: two-column -->
<section class="grid gap-3 xl:hidden">  <!-- NARROW: single-column -->
```

Tailwind semantics:

| viewport | `hidden xl:grid` | `xl:hidden` |
|---|---|---|
| **≥ 1280px** | `display: grid` — **live** | `display: none` |
| **< 1280px** | `display: none` | `display: grid` — **live** |

The two swap at Tailwind's `xl` breakpoint = **1280px**. Below it, the column
CLAUDE.md calls "the hidden duplicate" is the one on screen.

## 2. Where "mobile" is decided — three unaligned authorities

| # | Authority | Mechanism | Switches at |
|---|---|---|---|
| 1 | **The game** | Tailwind `sm/md/lg/xl` | 640 / 768 / 1024 / **1280** |
| 2 | **The skin's CSS** | 13 hand-picked `@media` widths | 420, 430, 520, 560, 600/601, 700, 780, 800, 860/861, 900, 1180 |
| 3 | **The skin's JS** | `[class~="xl:hidden"]` string test (UIFoundation) / `getBoundingClientRect()` (HeaderRenderer) / `(pointer: coarse)` (TooltipEngine) | 1280 (inverted) / live / device capability |

**Not one of the skin's eleven `max-width` values matches a Tailwind breakpoint.**
The skin's widest is 1180. The game's decisive switch is 1280. Between 1181 and
1279 the game has already collapsed to one column while every skin sheet is still
in full desktop mode — and that band contains the single most common desktop case,
a 1366×768 laptop.

## 3. What flows through the runtime, and what doesn't

`DOMWatcher` owns the only MutationObserver and emits `iw:dom-flush`. Every
classifier hangs off that event. Each caches *which element plays which role* and
revalidates cheaply — `isConnected`, the role attribute, containment, plus the
coverage guards added for the `[].every()` freeze.

**A viewport change produces none of those signals.** Resizing the window mutates
nothing: Tailwind flips `display` in CSS, the DOM is byte-identical. So:

- no mutation → no flush → no classifier runs;
- and when a flush *does* arrive (an idle game ticks constantly, so within a
  frame), every cached node is still `isConnected` and still carries its role
  attribute, so `*ResolutionValid` returns true and the classifier early-returns.

There is **no `resize` or `matchMedia` listener anywhere in the skin** except
`TooltipEngine`'s reposition. Nothing can invalidate a resolution on a layout
change, because nothing knows a layout change happened.

## 4. Audit — findings

### Verification performed

Playwright, driving **the real built `dist/content.bundle.js`** against a
reconstructed dual-column page: the game's two sections with their real Tailwind
classes, the real `@media (min-width:1280px)` rules, and a Tailwind-preflight-style
reset. Mutation bursts drive real flushes. Measured at 11 widths, cold boot and
after resize.

This is **not live-verified.** It reproduces the game's *layout contract*
(`hidden xl:grid` / `xl:hidden` + the xl media query), which is the thing under
test, but the real page's class soup is not here. Per this repo's own discipline:
only you can confirm on the live page.

### F1 — Every classifier inside the panel columns dies below 1280px  *(dominant)*

`UIFoundation` filters out `[class~="xl:hidden"]` in five places
([UIFoundation.js:348](src/modules/UIFoundation.js:348), [:456](src/modules/UIFoundation.js:456),
[:603](src/modules/UIFoundation.js:603), [:724](src/modules/UIFoundation.js:724),
[:753](src/modules/UIFoundation.js:753)). Above 1280 that is right. Below 1280 it
excludes the *visible* column and classifies the *hidden* one.

Sweep, cold boot at each width:

```
  w=1400  visibleFrame=true  visiblePanel=true  visibleBoss=true  || stranded: frame=0 panel=0 boss=0
  w=1320  visibleFrame=true  visiblePanel=true  visibleBoss=true  || stranded: frame=0 panel=0 boss=0
  w=1281  visibleFrame=true  visiblePanel=true  visibleBoss=true  || stranded: frame=0 panel=0 boss=0
  w=1280  visibleFrame=true  visiblePanel=true  visibleBoss=true  || stranded: frame=0 panel=0 boss=0
  w=1279  visibleFrame=false visiblePanel=false visibleBoss=false || stranded: frame=3 panel=3 boss=1
  w=1200  visibleFrame=false visiblePanel=false visibleBoss=false || stranded: frame=3 panel=3 boss=1
  w=1024  visibleFrame=false visiblePanel=false visibleBoss=false || stranded: frame=3 panel=3 boss=1
  w= 900  visibleFrame=false visiblePanel=false visibleBoss=false || stranded: frame=3 panel=3 boss=1
  w= 768  visibleFrame=false visiblePanel=false visibleBoss=false || stranded: frame=3 panel=3 boss=1
  w= 600  visibleFrame=false visiblePanel=false visibleBoss=false || stranded: frame=3 panel=3 boss=1
  w= 390  visibleFrame=false visiblePanel=false visibleBoss=false || stranded: frame=3 panel=3 boss=1
```

A one-pixel cliff at 1280 → 1279. Not a gradient, not a squeeze — a binary loss.

**Blast radius at 390px cold boot.** Lost entirely: section frames (the corner
filigree + forged ground on every panel), the three activity panels (Current
Action, Action Log, World Chat — title chrome, feed rows, progress, composer),
World Boss cards. Still working: header, main nav, zone bar, zone title, per-zone
theme, inventory root/rows, skill panels.

The survivors are exactly the modules that **don't** use the class test:

- `HeaderRenderer` resolves by `getBoundingClientRect()` tie-break — viewport-correct.
- `InventoryRenderer` resolves a row's root by *containment* (pair the row with its
  own heading's panel) — viewport-agnostic, correct by construction.
- `SkillPanelRenderer` is event-driven off `.compact-panel` — never asks which column.
- Header/nav/zone bar live *outside* both columns, so the question never arises.

That split is the refactor's whole argument: the two resolution strategies already
in the codebase both work at every width. Only the string test doesn't.

**This has already been patched around in CSS rather than fixed.**
[ui-system.css:432](src/styles/ui-system.css:432) carries a rule whose comment reads
"classifyFeed tags the … mirror's copy, not this visible one, so the
`[data-iw-panel-part="feed"]` rules never land here; hook the game class under our
(visible) panel attribute instead." That is F1, observed live, diagnosed as a CSS
problem and worked around at the leaf. There are almost certainly more of these.

### F2 — Nothing re-classifies on resize

Same page, resized rather than cold-booted:

```
### A. DESKTOP boot @1400
  WIDE   "hidden xl:grid" : onScreen=true  ui=11 panel=3 frame=5
  NARROW "xl:hidden"      : onScreen=false ui= 1 panel=0 frame=0

### C. RESIZE 1400 -> 900, after 4 mutation flushes
  WIDE   "hidden xl:grid" : onScreen=false ui=11 panel=3 frame=5
  NARROW "xl:hidden"      : onScreen=true  ui= 1 panel=0 frame=0
  >> decoration on VISIBLE column: 7    on HIDDEN column: 17
```

The decoration does not move. Flushes keep firing; every cached resolution stays
valid because `isConnected` is still true. Independent of F1: even with the
correct predicate, a resolution cached at one width would survive into the other.
Both must be fixed, or fixing F1 alone gives you a skin that is correct only at
the width it booted at.

### F3 — The skin's breakpoints don't align with the game's

Eleven `max-width` values, none matching 640/768/1024/1280. Consequences:

- **1181–1279** — the worst band. Game is single-column; skin is fully desktop.
  Header still runs its two-column `min-width: 861px` status-grid placement into a
  narrow stack.
- **769–780** — game is at `md`, skin still inside its `max-width: 780px` block.
- Sheets disagree with *each other*: at 880px `header.css` is in its 860–1180
  block while `ui-system.css` and `skillpanel.css` are already in their ≤900
  mobile blocks. Panel padding and frame border-width change 40px before the
  header does.

### F4 — Neither harness can see any of this

- `build-tools/fixtures/fixture.html` contains **zero** Tailwind responsive
  classes — the single `xl:hidden` occurrence is inside a comment. It models one
  hand-built column. `RESPONSIVE_WIDTHS = [320, 360, 390, 430, 600, 768]` renders
  that single column at six widths and audits it thoroughly. None of those
  measurements can fail for F1, F2 or F3, because the DOM shape that breaks isn't
  present.
- The desktop screenshot viewport is **1240** — below `xl`. On the real page that
  is already the game's mobile layout, so the "desktop" fixture is a composition
  the game never renders at that width.
- `tests/smoke.test.mjs` is jsdom with a synthetic single-column DOM: no layout,
  no media queries, no duplicate column.

This is CLAUDE.md's own "a fixture that models the wrong DOM shape lies exactly
like a missing stylesheet" — at whole-layout scale.

### F5 — Inline geometry ignores the viewport *(mis-diagnosed — see §8)*

`SkillPanelRenderer.styleButton()` writes `width/min-width/height` with
`!important` for the pager (26×44) and action button (155×44). CSS cannot override
inline `!important`, so `skillpanel.css`'s narrow-width blocks cannot resize
them. In a single-column stack at 360px, prev + action + next is a fixed
26+155+26 = 207px plus gaps inside a column that also has to hold the medallion
and the readout.

**Correction (§8 implementation, 2026-09-04): this is not actually a bug.**
Both fixed sizes are load-bearing, not desktop leftovers — 155px is `44px ×
3.52`, the `action_frame` art's aspect ratio, derived specifically to hold the
44px touch-target floor (see this file's own "True artwork ratios" section in
`skillpanel.css`); shrinking the width without shrinking the height below 44px
would distort the sprite, and shrinking both would violate the touch target.
26px is already at WCAG 2.5.8's practical floor for the nav pager's minor
axis. Neither value should respond to viewport width. The 360px-column
concern is real as a question but not as a finding: `render-fixtures.mjs`'s
existing `skillOverflow`/`mobileControlRail` checks already assert no overflow
at 320–390px, and pass — because the three-zone layout gives the command row
its own full-width grid row below that width, not because the buttons shrink.
De-inlining to chase F5 would have been actively harmful: it surfaced two
already-dead, already-superseded stylesheet rules (a `768px` `action-button`
width of 88px, and an older 44px-square nav-button rule from a since-replaced
sprite design) that are currently inert specifically *because* the inline
write wins — removing the inline write would have reactivated both and
reintroduced designs Curtis has since explicitly reversed. Left as-is;
annotated in place instead (`skillpanel.css`, the `768px` block).

### F6 — Two different "mobile" axes, silently crossed *(assessed, not fixed — see §8)*

`TooltipEngine.isMobile()` / `NameScanner` use `(hover: none), (pointer: coarse)`
— a *device capability*. The CSS uses *width*. A touchscreen laptop at 1400px gets
mobile tooltips on a desktop layout; a narrow mouse-driven window at 390px gets
desktop tooltips inside the CSS's `max-width: 420px` block. Both axes are
individually defensible; the bug is that neither knows about the other.

**Assessment (§8 implementation, 2026-09-04):** on reflection this is arguably
correct behavior, not a bug — a tooltip's tap-vs-hover interaction model
should follow input capability, not window width; `pointer: coarse` genuinely
is the right question for "will a hover-and-linger gesture work here", which
narrow-vs-wide viewport cannot answer. The compact CSS layout should (and
does) follow width, since that is a layout question. Left unchanged;
flagging it as "needs your call" was itself the overreach — there is no
concrete failure mode named here beyond "two systems use different signals
for different questions," which is the correct design, not a coincidence to
reconcile.

## 5. Refactor plan

Ordered by value. Steps 1 and 2 together fix the break; 3–5 make it stay fixed.

### Step 1 — Replace the class test with runtime visibility (fixes F1)

Add `src/modules/Viewport.js` and generalise the pattern `HeaderRenderer` already
proved:

```js
// Rendered = actually painting. Bare checkVisibility() already returns false for
// a `display:none` ancestor, which is exactly the column-swap case, so no options
// object is needed — and avoiding one dodges the checkVisibilityCSS ->
// contentVisibilityAuto/opacityProperty option rename. Chrome 105+; the manifest
// targets chrome109. The rect is the fallback for anything older.
export function isRendered(el) {
  if (!el?.isConnected) return false;
  if (typeof el.checkVisibility === 'function') return el.checkVisibility();
  const r = el.getBoundingClientRect?.();
  return !!r && (r.width > 0 || r.height > 0);
}

// TIE-BREAK, never a hard filter: jsdom lays nothing out, so if NOTHING looks
// rendered, every candidate is returned. This is the exact reasoning already
// written at HeaderRenderer.js:161 — keep it, it is what stops the test suite
// from resolving to nothing.
export function preferRendered(candidates) {
  const live = candidates.filter(isRendered);
  return live.length ? live : candidates;
}
```

Then at the five sites, `!el.closest('[class~="xl:hidden"]')` becomes
`preferRendered(...)` over the candidate list. Note the shape change: the class
test is a per-element predicate, `preferRendered` is a list operation — so
`sectionFrameHeadings()` and `bossHeadings()` filter their array through it, and
the two single-element sites (`:603`, `:753`) use `isRendered` with the
"if nothing is rendered, accept it" fallback preserved.

**Why this and not a media-query test.** `matchMedia('(min-width:1280px)')` would
also fix the swap, but it hardcodes the game's Tailwind config into the skin and
still can't see conditional rendering, a collapsed accordion, or a route that
mounts only one column. Visibility is the property actually being asked about.

**Do not delete the `xl:hidden` knowledge.** Keep it as a cheap pre-filter *only*
where it is provably safe, or drop it entirely — but the CLAUDE.md trap note must
be rewritten, because "never frame the `xl:hidden` copy" is only true above 1280.

### Step 2 — Make a viewport change a first-class invalidation signal (fixes F2)

`DOMWatcher` is the event hub; give it a second, non-mutation source.

```js
// Coarse layout epoch. Bumped when the viewport crosses a boundary that can
// change which nodes are painted. Cheap: one number, compared not scanned.
let layoutEpoch = 0;
export const getLayoutEpoch = () => layoutEpoch;
```

Watch the *game's* breakpoints, not arbitrary resize events — `matchMedia` change
events fire only on a crossing, so this costs nothing while a user drags a window
inside one band:

```js
const QUERIES = [640, 768, 1024, 1280, 1536].map(px => matchMedia(`(min-width:${px}px)`));
const onCross = () => { layoutEpoch += 1; emit('iw:dom-flush', { roots: [] }); };
// register in startWatcher, remove in stopWatcher — lifecycle-owned like the observer
```

Then every classifier's cache-validity function gains one term:
`entry.epoch === getLayoutEpoch()`. That is strictly cheaper than adding a
visibility check to each `*ResolutionValid`, and it invalidates *all* of them
together, which is what a column swap actually requires.

Two constraints this respects:
- Still **one MutationObserver**. A `matchMedia` listener is not an observer and
  does not feed the mutation queue.
- The emitted flush carries `roots: []`, which `content.js` already handles as the
  whole-document repaint case.

**Also:** stale role attributes on the now-hidden column must be cleared, or a
`[data-iw-panel="action-log"]` sits on an invisible node and any future `:has()`
or coverage logic counts it. Simplest correct approach: on an epoch bump, run each
module's `clear*()` for the affected roles before re-resolving.

### Step 3 — Realign the CSS breakpoints to the game's (fixes F3)

Collapse thirteen ad-hoc widths onto Tailwind's scale, since the game's layout is
what the skin is decorating:

```css
/* base.css — one source of truth, documented next to the token layer */
/*  xl  1280  the panel-column swap. THE breakpoint. Skin must collapse here. */
/*  lg  1024  two-up panel grids go single                                     */
/*  md   768  tablet: frame padding, plaque height                             */
/*  sm   640  phone: stack command rows, shrink medallions                     */
```

Migration is mechanical and low-risk if done in this order:

1. Add the `xl` (1280) block the skin currently lacks — this alone fixes the
   1181–1279 dead band, and is the highest-value CSS change.
2. Move `1180 → 1280`, `900/860 → 1024`, `800/780/700 → 768`, `600/601 → 640`.
3. Leave `560/520/430/420` as a single `sm`-and-below tier, or keep one narrow
   phone tier at 430 for the tooltip/plaque cases that genuinely need it — but
   pick *one* value and use it in all six sheets.

Do this **after** steps 1–2, not before: with F1 live, you cannot tell whether a
CSS change helped, because the rules aren't landing on the visible nodes anyway.

### Step 4 — Give the renderers a viewport input (fixes F5)

`styleButton()` writes inline `!important`, so this cannot be solved in CSS. Two
options, in preference order:

- **Preferred:** stop writing geometry inline. Move `width`/`height` into
  `skillpanel.css` and keep inline only what genuinely cannot be a rule (the
  computed sprite window). Then existing media queries reach it. Requires checking
  the `ui-system.css` `:not()` chain covers the skill controls — it already lists
  them.
- **If inline must stay:** read the epoch/breakpoint from `Viewport.js` and write
  the tier-appropriate constant, re-running on epoch bump. Keeps the duplication
  CLAUDE.md already warns about (nav width 26px, action 155×44 exist in two
  places) but at least makes it viewport-aware.

### Step 5 — Make the harnesses capable of failing (fixes F4)

Without this the fix is unpinned and will regress.

1. **Fixture:** wrap the panel stack in the real two-section shape with the real
   `hidden xl:grid` / `xl:hidden` classes and the real `@media (min-width:1280px)`
   rules. This is the single highest-value harness change in the project — it is
   the DOM shape three of these five findings live in.
2. **`RESPONSIVE_WIDTHS`:** add `1279` and `1281`. The pair straddling the swap is
   the assertion that matters.
3. **New `tests/viewport-swap.test.mjs`** (Playwright, not jsdom — jsdom cannot do
   this): boot at 1400, assert decoration is on the wide column; resize to 900,
   assert it has *moved* to the narrow column and that the wide column is clean.
   Then cold-boot at 390 and assert the same end state.
4. **Negative control, per project discipline:** revert step 1 and confirm the new
   test fails. The sweep in F1 is that control today — it produces
   `visibleFrame=false` against current `main`.
5. Move the desktop fixture screenshot viewport from **1240 to ≥1281**, so it
   renders the layout the game actually shows at desktop.

## 8. Implementation record (2026-09-04)

**Step 2 — `Viewport.js` + replace the 5 exclusion sites.** Done as planned,
plus one thing the plan didn't call out: `resolveMainNav()` had the identical
bug in a different shape — "first match in document order wins" per nav label,
with only ONE `mainNavResolution` ever cached (not one per column). Found
because `HeaderRenderer.classifyAdjacent()` already defends against a
duplicated `[data-iw-ui="main-nav"]` via `pickVisible`, which only makes sense
if more than one can exist — but `classifyMainNav` never tagged more than one.
Fixed with the same `pickRendered`-per-label approach. `classifyZoneBar` did
**not** need this: it already loops over every matching label branch and tags
each column's copy independently, so both columns end up correctly tagged and
CSS (not JS selection) is what makes only the visible one paint.

**Step 3 — layout epoch.** Done. One subtlety the plan didn't anticipate:
`sectionFrameResolutions`/`bossPanelResolutions`'s own coverage check
(`headings.every(h => seen.has(h))`) turned out to already self-heal on
resize, because their heading-scan functions are themselves viewport-aware
(re-run fresh every classify call) — the epoch check there is defense in
depth, not load-bearing. `activityPanelResolutions`'s coverage check is
keyed by **panel slug**, not by node, so it does NOT self-heal — the epoch
check there is the actual fix. Also added stale-mark cleanup on re-resolve
to `classifyBossCards`/`classifyMarket` (mirroring the pattern
`classifySectionFrames`/`classifyActivityPanels` already had), since without
it a resize left `data-iw-boss`/`data-iw-market` stuck on the newly-hidden
column forever.

**Step 4 — pinning test.** `tests/viewport-swap.test.mjs`, real-browser
(Playwright), covers cold boot below 1280px, resize in both directions, and a
repeated round-trip. **Negative control actually run**, not just claimed: the
fix was stashed, the test was run against the pre-fix bundle and failed with
9 concrete assertion failures, then the fix was restored and reconfirmed
green. `static-invariants.test.mjs` also updated — it used to hard-*require*
the buggy `[class~="xl:hidden"]` string test as an invariant; it now requires
the opposite plus requires `Viewport.js`/`preferRendered`/`getLayoutEpoch`
usage, so the old bug pattern can't quietly return.

**Step 5 — breakpoint realignment.** Done for the **upper tiers only**:
`900/860→1024` (lg), `800/780/700→768` (md), `600/601→640` (sm),
`1180→1280` (xl, header.css's dead-band fix). The **lower tier** (`560/520/
430/420`) was deliberately left untouched — collapsing four sub-breakpoints
into one risked changing behavior in the gaps between them with no way to
verify visually against the live game, and the plan itself flagged this as
optional ("or keep one narrow phone tier"). This was a mechanical
value-substitution only — no rule bodies, ordering, or logic changed, just
which pixel width each existing rule fires at.

The renumbering surfaced a real coupling risk: `render-fixtures.mjs` hardcodes
several of the *exact same* pixel values as assertion thresholds (`width <=
700`, `width <= 600`, `viewportWidth <= 600` in three places, plus a
regex-pinned `@media (max-width: 700px)` in `static-invariants.test.mjs`).
